# Stitch Dataverse customization history from partial sources

Dataverse has no native log that tells you who changed a form, column or view and what they changed. Microsoft states plainly that auditing **"isn't supported on table or column definition changes"** ([Manage Dataverse auditing](https://learn.microsoft.com/en-us/power-platform/admin/manage-dataverse-auditing)). The Audit table's only customization-related events are table and column deletions, changes to audit settings, and security-role edits. A utility that tracks customization history is still feasible, as long as it is built as a correlation engine and not as a reader of a log that does not exist. **"What changed" and "when" can be fully recovered by polling and diffing snapshots.** RetrieveMetadataChanges covers tables, columns and choices. Row polling of systemform, savedquery, webresource and related tables covers forms, views and scripts. **"Who" is the hard part.** The native identity signals each have a gap. Last-writer `modifiedby` columns are missing on `systemform`. Purview activity logs cover production environments only and record message names without before/after values. Plug-ins can be registered on web resources but not on forms or views. ALM identities (Git commits, pipeline requesters) attribute deployments, not individual edits. The recommended design has two parts. A per-environment snapshot ledger becomes your own system of record. Pluggable attribution adapters attach candidate actors to each detected change, with an explicit confidence level. No XrmToolBox, Microsoft or commercial tool could be found that does this today, so the gap is real. Several make-or-break behaviors are undocumented, though, and must be tested before you freeze the design: whether forms and views can be audited, whether PublishXml accepts plug-in steps, and what Purview actually records for metadata messages.

## Native auditing stops at deletes, audit toggles and role edits

Dataverse auditing records row-level create, update and delete operations on tables whose `IsAuditEnabled` managed property is on. It is "supported on all custom and most customizable tables and columns". The same page excludes definition changes, retrieves and exports ([Manage Dataverse auditing](https://learn.microsoft.com/en-us/power-platform/admin/manage-dataverse-auditing)). The Audit table's `action` choice set confirms this. Its customization-flavoured codes are **100 Delete Entity, 101 Delete Attribute, 102–104 audit changes at table, column and org level, 105–111 audit started, stopped and log-deletion events, and 53–59 role assignment and role-privilege changes**. No code exists for creating or updating a table or column, publishing, or importing a solution ([Audit table reference](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/reference/entities/audit)). Microsoft's developer guide groups 100–104 as "metadata change events". Read the label narrowly: it means "user deleted a table", "user deleted a column", "user changed a table definition to enable or disable auditing" and "user changed organization settings" ([Retrieve the history of audited data changes](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/auditing/retrieve-audit-data)). The same article says `operation` has four values. The generated reference lists ten, including an undocumented `200 CustomOperation`, which is a reminder that the documentation itself drifts.

Within that narrow band, the Audit table is genuinely useful. It gives authoritative **who and when for table and column deletions**. It records **audit-setting tampering**. It captures **security-role privilege changes with old and new privileges** through `RolePrivilegeAuditDetail` ([Retrieve the history of audited data changes](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/auditing/retrieve-audit-data)). No source says whether the payload of a 100/101 event keeps the deleted table's or column's name, so a utility has to snapshot names beforehand to make those events readable.

The bigger open question is whether the component tables themselves can be audited. Microsoft publishes a list of tables whose `CanModifyAuditSettings` is false, and it includes **Workflow and WorkflowLog** ([Manage Dataverse auditing](https://learn.microsoft.com/en-us/power-platform/admin/manage-dataverse-auditing)). Workflow is the table that stores processes such as classic workflows and business rules, so native auditing cannot cover them. `solution` and `entity` appear in the "Common entities across Dynamics 365 apps" preset ([Manage Dataverse auditing](https://learn.microsoft.com/en-us/power-platform/admin/manage-dataverse-auditing)). No document states the audit status of `systemform`, `savedquery`, `savedqueryvisualization`, `webresource`, `sitemap`, `appmodule` or `solutioncomponent`. The supported check is to read `IsAuditEnabled` (its `Value` and `CanBeChanged`) from `EntityDefinitions` in each environment ([Configure auditing](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/auditing/configure)). Even if a table can be audited, nobody has documented whether maker-portal saves, publishes or solution imports produce audit rows.

Where data is audited, the constraints still bite. Old and new values are **capped at about 5 KB** and truncated with an ellipsis, which makes native audit useless for diffing `formxml`, `fetchxml`/`layoutxml` or Base64 web resource content. Audit data is **not exposed through the TDS (SQL) endpoint**. A query supports only one link-entity, and only to systemuser. The Web API leaves out `ChangeData`. `RetrieveRecordChangeHistory` over the Web API returns no "who" or "when", so a Web API client has to join back to `audits` ([Retrieve the history of audited data changes](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/auditing/retrieve-audit-data)). Retention is documented inconsistently. The admin guide says the default is Forever with a 24,855-day maximum ([Manage Dataverse auditing](https://learn.microsoft.com/en-us/power-platform/admin/manage-dataverse-auditing)). The developer article says the default is 30 days with a 1–365,000-day range ([Configure auditing](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/auditing/configure)). Read `auditretentionperiodv2` per environment rather than assuming either. Nothing on the roadmap closes the gap. The September 2025 auditing announcement added AI-agent events, original choice labels, per-table retention and masked-field auditing, and **no metadata auditing** ([Power Platform Blog, 2025-09-11](https://www.microsoft.com/en-us/power-platform/blog/2025/09/11/dataverse-auditing/)).

## Every native "who" signal is partial, overwritten or production-only

### Component rows keep only the last writer, and forms keep none

The cheapest "who" signal is the standard ownership columns, and they are uneven. `savedquery` (views) has `CreatedBy`, `ModifiedBy` ("Shows who last updated the record"), `ModifiedOn` and the `OnBehalfBy` variants ([SavedQuery](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/reference/entities/savedquery)). So do `savedqueryvisualization` ([SavedQueryVisualization](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/reference/entities/savedqueryvisualization)), `webresource` ([WebResource](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/reference/entities/webresource)) and `solution` ([Solution](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/reference/entities/solution)). **`systemform` has no CreatedBy, CreatedOn, ModifiedBy or ModifiedOn at all.** Its only time signals are `PublishedOn` and an "internal use only" `OverwriteTime`, and it has no relationships to systemuser ([SystemForm](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/reference/entities/systemform)). Table and column definitions expose `CreatedOn` and `ModifiedOn` but no user property ([EntityMetadata](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/reference/entitymetadata); [AttributeMetadata](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/webapi/reference/attributemetadata)).

Where these columns exist, they hold one value that the next edit overwrites. Community practice shows the problem. In a Dynamics Community thread about unexplained form changes, a Microsoft employee said "there is no OOB feature support yet" and suggested querying `solutioncomponent.modifiedby`. The poster noted that the query only helps if you run it before someone else edits the component ([Dynamics Community: Audit trail – form changes](https://community.dynamics.com/forums/thread/details/?threadid=651d3ab5-fcc4-ee11-9079-00224822dc70)). That workaround is weaker than it looks. `solutioncomponent` rows describe solution *membership*, not edits to the component ([SolutionComponent](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/reference/entities/solutioncomponent)). Practitioners widely assume that a solution import stamps the importing user or service principal into `modifiedby`, but no Microsoft source confirms this, so it has to be tested.

### Purview logs the message, not the change

Microsoft Purview's Dataverse activity logging is the only native stream that plausibly records **every customization call with a user identity**. Logging happens "at the SDK layer", and the system "logs all SDK messages except" a short exclusion list. That list contains metadata *reads* (`RetrieveAttribute`, `RetrieveMetadataChanges`, `RetrieveEntityChanges`) but no metadata writes or ALM messages ([Dataverse activity logs in Purview](https://learn.microsoft.com/en-us/power-platform/admin/activity-logging-auditing/activity-logs-dataverse-model-driven-apps)). By that rule, CreateAttribute, UpdateEntity, PublishXml, PublishAllXml, ImportSolution and Update on `systemform` should all be logged. No current Microsoft page names them, though, and the only corroboration is a 2018 community gist. The gist shows `PublishAllXml` as a logged item, an empty-GUID `EntityId` for publish, and `EntityName` "Unknown" for import solution ([GitHub gist: Schema_Dynamics365_ActivityLogging](https://gist.github.com/fordosa90/a798290f68006968cfcd995bae8cbc01)).

Each event carries `UserUpn`, `UserKey`, `SystemUserId`, a UTC `CreationTime`, `Message`, `EntityName`/`EntityId` and `CorrelationId`. **It carries no before/after values**: "the details of each column's before-and-after values for CRUD activites are not sent to Purview activity logging". Records over 3 KB are split and must be regrouped by `CorrelationId`. Some records arrive with `EntityName` "Unknown" and an all-zero `EntityId` ([Dataverse activity logs in Purview](https://learn.microsoft.com/en-us/power-platform/admin/activity-logging-auditing/activity-logs-dataverse-model-driven-apps)). The schema still describes `Fields` as holding "values that were created or updated", which contradicts the no-before/after note, so treat `Fields` as unreliable. In practice Purview most likely gives you "user X called UpdateAttribute at time T" without naming the column. For forms and views, it probably shows an Update on `systemform` or `savedquery` with the record id, which identifies the component but not the change.

The prerequisites are substantial. **Activity logs reach Purview "only for production environments"**, and only when the minimum Office licensing is met ([Power Platform activity logging overview](https://learn.microsoft.com/en-us/power-platform/admin/activity-logging-auditing/activity-logs-overview)). The environment needs auditing started with "Read logs" on ([Manage Dataverse auditing](https://learn.microsoft.com/en-us/power-platform/admin/manage-dataverse-auditing)). Each production environment also needs the newer **"Enable SAS Logging in Purview"** setting, plus an allow-list entry for `*.api.powerplatformusercontent.com` ([Power Platform activity logging overview](https://learn.microsoft.com/en-us/power-platform/admin/activity-logging-auditing/activity-logs-overview)). Audit (Standard) keeps records **180 days**. Audit (Premium) retention policies can extend that. Records from non-user entities such as service principals are kept a fixed one year ([Purview auditing solutions overview](https://learn.microsoft.com/en-us/purview/audit-solutions-overview)).

There are two programmatic paths. The first is Microsoft Graph `POST /security/auditLog/queries` (v1.0), with `AuditLogsQuery-CRM.Read.All`, `recordTypeFilters: ["crm"]` and `operationFilters`. It is asynchronous, subject to tenant daily limits, and available in the Global cloud only ([Graph: Create auditLogQuery](https://learn.microsoft.com/en-us/graph/api/security-auditcoreroot-post-auditlogqueries)). The second is the Office 365 Management Activity API `Audit.General` feed. It can only look back seven days, returns events out of order, and can take up to 12 hours after subscription to deliver its first content ([Office 365 Management Activity API reference](https://learn.microsoft.com/en-us/office/office-365-management-api/office-365-management-activity-api-reference)). Typical availability is **60–90 minutes after the event, sometimes longer** ([Purview audit search](https://learn.microsoft.com/en-us/purview/audit-search)). Microsoft also warns that future releases will stop logging operations "deemed unnecessary" ([Dataverse activity logs in Purview](https://learn.microsoft.com/en-us/power-platform/admin/activity-logging-auditing/activity-logs-dataverse-model-driven-apps)), so event coverage is not a stable contract.

The adjacent pipelines add little. Microsoft Sentinel ingests the same stream into `DataverseActivity` ([DataverseActivity table](https://learn.microsoft.com/en-us/azure/azure-monitor/reference/tables/dataverseactivity)). Its roughly 35 built-in Dataverse rules include "Audit logging disabled", "Organization settings modified" and "Suspicious security role modifications", but **none for solution imports, publishes or schema changes**, so you would need custom KQL ([Sentinel security content reference](https://learn.microsoft.com/en-us/azure/sentinel/business-applications/power-platform-solution-security-content)). The Power Platform admin activity log covers environment lifecycle, settings, DLP and `ApplyAdminRole`. It has **no solution or customization events**, though environment copy, restore and reset are useful context because they replace customizations wholesale ([Power Platform admin activity logs](https://learn.microsoft.com/en-us/power-platform/admin/activity-logging-auditing/activity-logs-power-platform-admin)). Application Insights export does put the user's Entra object id on every row and records SDK calls as `dependencies` with `type` "SDK &lt;Message&gt;" ([App Insights integration overview](https://learn.microsoft.com/en-us/power-platform/admin/overview-integration-application-insights); [Telemetry events for Dataverse](https://learn.microsoft.com/en-us/power-platform/admin/telemetry-events-dataverse)). But it requires Managed Environments, delivers with a **24-hour SLA**, and is positioned as performance data, not audit data ([Export data to Application Insights](https://learn.microsoft.com/en-us/power-platform/admin/set-up-export-application-insights)). Its one advantage is that it is not limited to production, which makes it a best-effort signal for managed non-production environments.

### Plug-ins reach web resources, and perhaps publish

Synchronous capture through the event pipeline would be ideal, but Microsoft closes most of that door: "The platform doesn't make available any operations that involve table definitions" ([Event Framework](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/event-framework)). The generated table references mark **Create, Update and Delete as non-events on `systemform`, `savedquery`, `savedqueryvisualization`, `solution` and `solutioncomponent`**. **`webresource` Create, Update and Delete are events** ([SystemForm](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/reference/entities/systemform); [SavedQuery](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/reference/entities/savedquery); [WebResource](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/reference/entities/webresource)). A PostOperation step on `webresource`, with pre- and post-images, therefore records exactly who changed which script and what the content was before and after ([Understand execution context](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/understand-the-data-context)). It can stream to Service Bus or a webhook through `RemoteExecutionContext` ([Event Framework](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/event-framework)).

The undocumented prize is **PublishXml**. Its `ParameterXml` lists the entities, forms and web resources being published ([PublishXmlRequest.ParameterXml](https://msdn.microsoft.com/en-in/library/gg326512(v=crm.8))). A 2017 community plug-in logged PublishXml and PublishAllXml to a custom "Publish Log" table, which suggests the messages accepted steps at that time. Its author noted that **PublishAllXml carries no ParameterXml**, so "it's not possible to know which components are involved" ([fedejousset.com: Audit Publish & PublishAll events](https://www.fedejousset.com/2017/03/13/audit-publish-publishall-events/)). Publish logging has a second gap: creating or deleting a component publishes automatically, without an explicit publish call ([Publish customizations](https://learn.microsoft.com/en-us/dynamics365/customerengagement/on-premises/developer/customize-dev/publish-customizations?view=op-9-1)). Whether PublishXml, ImportSolution or ExportSolution accept custom steps in online environments today has to be settled with Microsoft's documented `sdkmessagefilter` query (`iscustomprocessingstepallowed eq true`) ([Event Framework](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/event-framework)).

### ALM identities attribute deployments, not edits

Native Dataverse Git integration is Microsoft's own answer. The FAQ says using it "to audit metadata changes" is "common", and commits can be triggered through the `CommitToGit` API ([Git integration FAQs](https://learn.microsoft.com/en-us/power-platform/alm/git-integration/faqs)). Its limits are hard ones. It requires Managed Environments and is meant for development environments only ([Git integration overview](https://learn.microsoft.com/en-us/power-platform/alm/git-integration/overview)). It forces you to commit **all pending changes in a solution at once** ([Git integration FAQs](https://learn.microsoft.com/en-us/power-platform/alm/git-integration/faqs)). No document says which identity becomes the commit author, and on GitHub, which is still in preview, the GitHub App handles communication rather than individual users ([Connect to GitHub](https://learn.microsoft.com/en-us/power-platform/alm/git-integration/connecting-to-github)). Git history is therefore an excellent record of *what* and *when committed*, and a weak record of *who edited each component*. Power Platform Pipelines keep 365 days of run history. The documented fields do not include a requester ([Admin deployment page](https://learn.microsoft.com/power-platform/alm/admin-deployment-hub)). Microsoft's own GitHub Actions pattern instead takes `DeployAsUser` from the deployment trigger as the commit author ([Extend pipelines using GitHub Actions](https://learn.microsoft.com/en-us/power-platform/alm/extend-pipelines-github-export)). Solution history (`msdyn_solutionhistory`) records operation, sub-operation, version, start and end time, and result. It has **no user column**, and rows are purged after **180 days** ([View the history of a solution](https://learn.microsoft.com/en-us/power-apps/maker/data-platform/solution-history); [msdyn_solutionhistory](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/reference/entities/msdyn_solutionhistory)).

| Source | Who | When | What changed | Coverage and prerequisites | Native retention |
|---|---|---|---|---|---|
| Audit table | `userid`, `callinguserid` | Millisecond `createdon` | Table/column deletes, audit toggles, role privileges; old/new values capped at ~5 KB | Component-table auditability undocumented; Workflow not auditable | Per-environment setting; docs conflict |
| `modifiedby`/`modifiedon` | Last writer only | Last write only | None | savedquery, savedqueryvisualization, webresource, solution; **not systemform**; metadata has no user | Overwritten on next edit |
| Purview / Sentinel `DataverseActivity` | UPN, Entra id, systemuser id | UTC, 60–90+ min latency | Message name plus entity; no before/after | **Production only**; auditing, Read logs, SAS logging setting | 180 days (Standard) |
| App Insights export | Entra object id | 24-hour SLA | URL or "SDK &lt;Message&gt;" | Managed Environments only | 90 days default in Log Analytics ([Azure Monitor retention](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/data-retention-archive)) |
| Plug-in step | Execution-context user | Exact | Full pre/post images | `webresource` confirmed; PublishXml unverified; forms and views blocked | Your own store |
| Solution history | None | Start/end | Solution operation and version | All environments | 180 days |
| Component layers | None | "Overwrite Time" | Layer JSON and changed properties | Single unmanaged layer | Current state only |

## Polling and snapshots recover "what" and "when" completely

Microsoft is explicit that schema changes must be polled: "No event exists to detect when schema definition changes occur" ([Cache schema data](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/cache-schema-data)). **RetrieveMetadataChanges** is purpose-built for this. You pass the previous `ServerVersionStamp` as `ClientVersionStamp` with the same query, and you get back only tables, columns, relationships and choices that changed. `HasChanged` flags tell you whether a node itself changed or only something beneath it. With `DeletedMetadataFilters`, you also get the MetadataIds of deleted items. Three caveats apply. Change data lasts **90 days by default** (`Organization.ExpireSubscriptionsInDays`), and an expired or invalidated stamp throws `ExpiredVersionStamp` (0x80044352), sometimes earlier because of system maintenance. Deleted choice *options* are not tracked individually, so you have to compare option lists yourself. And requesting deletions bypasses the internal cache and costs performance ([Cache schema data](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/cache-schema-data)). Because `RetrieveMetadataChanges` is on Purview's exclusion list, a frequent poller does not flood the activity log ([Dataverse activity logs in Purview](https://learn.microsoft.com/en-us/power-platform/admin/activity-logging-auditing/activity-logs-dataverse-model-driven-apps)). The `ModifiedOn` values on `EntityMetadata` and `AttributeMetadata` narrow the "when" inside a poll window.

Forms, views, charts and web resources are rows, not metadata, so they need row polling and full-content snapshots. The payloads to capture are `FormXml`/`FormJson` on systemform, `FetchXml`/`LayoutXml`/`LayoutJson` on savedquery, `DataDescription`/`PresentationDescription` on savedqueryvisualization, and Base64 `Content` on webresource. `ComponentState` marks unpublished edits, and the `RetrieveUnpublished`/`RetrieveUnpublishedMultiple` messages let a tracker diff pending changes against published ones ([SystemForm](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/reference/entities/systemform); [SavedQuery](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/reference/entities/savedquery); [WebResource](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/reference/entities/webresource)). Dataverse has no incremental form update, so every save sends the complete FormXml ([TALXIS tools-cli notes](https://github.com/TALXIS/tools-cli/blob/master/docs/dataverse-metadata-performance.md)). The utility has to store full snapshots and compute diffs itself. Imports complicate this further. "Overwrite Customizations has no effect" on forms, because incoming forms merge with existing layers ([How managed solutions are merged](https://learn.microsoft.com/en-us/power-platform//alm/how-managed-solutions-merged)). A post-import form can therefore differ from both the source and the prior target state, and only a post-import snapshot shows what the user actually sees.

Component layers add context that snapshots alone lack. The virtual table `msdyn_componentlayer` returns one row per layer, with the solution and publisher, a uniform JSON definition (`msdyn_componentjson`), the changed properties (`msdyn_changes`) and an "Overwrite Time" ([msdyn_componentlayer](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/reference/entities/msdyn_componentlayer)). It answers "is this change an unmanaged edit or did managed solution X bring it?" Layers have no history of their own, though. The unmanaged layer "is a single layer", so successive edits by different makers collapse into one ([Solution layers](https://learn.microsoft.com/en-us/power-apps/maker/data-platform/solution-layers)). Solution history supplies the deployment timeline: Import, Uninstall, Export, Publish and PublishAll operation codes with start and end times ([msdyn_solutionhistory](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/reference/entities/msdyn_solutionhistory)). Copy it at least daily to get past the 180-day purge. The pac CLI (`export`, `clone`, `sync`, `unpack`) remains a fallback snapshot path. The documentation is inconsistent about whether `clone` and `unpack` support the YAML format that native Git integration writes ([pac solution reference](https://learn.microsoft.com/en-us/power-platform/developer/cli/reference/solution); [Git integration FAQs](https://learn.microsoft.com/en-us/power-platform/alm/git-integration/faqs)), so pick one canonical format for the ledger and don't mix them.

## Build a snapshot ledger with pluggable attribution adapters

Nobody ships this today, which justifies building it. The audit-named XrmToolBox tools work on record-data auditing or on audit configuration. Audit Center, for example, "allows you to define audit settings" ([XrmToolBox: Audit Center](https://www.xrmtoolbox.com/plugins/MscrmTools.AuditCenter)). The Solution History plugin shows imports but not exports or uninstalls ([NuGet: Ryr.XrmToolBox.SolutionHistory](https://www.nuget.org/packages/Ryr.XrmToolBox.SolutionHistory)). The comparers diff two states at a single point in time ([XrmToolBox plugin list](https://www.xrmtoolbox.com/plugins/)). The CoE Starter Kit is "no longer actively maintained" and inventories solutions, not components ([Set up the CoE Starter Kit](https://learn.microsoft.com/power-platform/guidance/coe/setup)). The design that fits the evidence treats **your own ledger as the system of record**. Every native source becomes either a *detector* of what changed or an *attributor* of who changed it.

```
 per environment (scheduled, app user)         tenant level                      ALM
 ┌───────────────────────────────────┐   ┌──────────────────────────┐   ┌──────────────────────┐
 │ Schema poller  (RetrieveMetadata- │   │ Purview adapter (Graph   │   │ Git commits,         │
 │   Changes + full re-baseline)     │   │  auditLogQuery / O365    │   │ Pipeline DeployAsUser│
 │ Row poller (form/view/chart/WR/   │   │  Mgmt API / Sentinel)    │   └──────────┬───────────┘
 │   sitemap/appmodule + unpublished)│   │ App Insights (optional)  │              │
 │ Solution-history + audit pollers  │   └────────────┬─────────────┘              │
 │ Layer enrichment (changed items)  │                │                            │
 │ Plug-ins: webresource, PublishXml?│                │                            │
 └────────────────┬──────────────────┘                │                            │
                  ▼                                   ▼                            ▼
        Snapshot ledger + change events ──► Correlation engine (time window, component id,
        (full XML/JSON, diffs, watermarks)     user, CorrelationId) ──► attribution + confidence
```

**The detection side runs per environment** under an application user with metadata read rights and `prvReadAuditSummary` ([Retrieve the history of audited data changes](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/auditing/retrieve-audit-data)). The schema poller keeps its version stamp and a full snapshot. When it hits `ExpiredVersionStamp`, it re-queries everything and diffs against the last snapshot, so no change is lost silently. One approach is to run a cheap stamp chain often and a second chain with `DeletedMetadataFilters` less often, because the deletion query is the expensive one. Audit actions 100/101 back up deletions with a user identity. The row poller filters on `modifiedon` watermarks where the column exists and records `modifiedby` *at detection time*, before a later edit overwrites it. For `systemform` it falls back to hashing `formxml`/`formjson` together with `publishedon` and `versionnumber`. Poll every 5–15 minutes. Short intervals narrow the "when" window and cut the chance that two makers' edits merge into one observed change. For every changed component, the layer step queries `msdyn_componentlayer` to label it as an unmanaged edit or a managed-solution arrival. Solution history and audit rows go into the ledger daily, ahead of their purge windows.

**The attribution side runs as adapters, each with a known confidence.** A plug-in step or an audit row on the exact component is *direct* evidence. A Purview `Update` on the same `systemform`/`savedquery` id within the detection window is *corroborated*. A `modifiedby` captured at poll time is *last-writer*: it is reliable when only one edit occurred in the window and ambiguous otherwise. A change that falls inside a solution-history import window is *deployment-attributed*: it is attributed to "solution X v1.2.3", and to a deployer when a Purview `ImportSolution` event or a Pipelines `DeployAsUser` lines up. Anything else is *unattributed*, and the utility should label it that way rather than guess. Purview and App Insights deliver late (60–90 minutes typically, and up to 24 hours for App Insights), so the correlation engine has to re-run on older changes at intervals such as 2 hours and 24 hours ([Purview audit search](https://learn.microsoft.com/en-us/purview/audit-search); [Export data to Application Insights](https://learn.microsoft.com/en-us/power-platform/admin/set-up-export-application-insights)). Pull Purview through Graph `operationFilters` scoped to customization messages, not the full CRM feed, because every read is also logged ([Graph: Create auditLogQuery](https://learn.microsoft.com/en-us/graph/api/security-auditcoreroot-post-auditlogqueries)). Each native source expires on its own schedule: version stamps after 90 days, solution history and Purview Standard after 180 days, and audit retention possibly after 30 days. **The ledger has to persist its own copy of every signal it relies on.**

**Environment strategy decides how much attribution the tool has to do.** In production, Purview supplies the "who", and turning on **Block unmanaged customizations** makes almost any detected unmanaged change an incident in its own right. That setting blocks unmanaged imports, new components and unmanaged changes to managed components. Dataflows are exempt and still create unmanaged layers ([Block unmanaged customizations](https://learn.microsoft.com/en-us/power-platform/alm/block-unmanaged-customizations)). In development, Purview is blind. Use Git integration with scheduled `CommitToGit` calls where Managed Environments are licensed. Rely on `modifiedby` and plug-ins elsewhere. Where you can, give each maker their own development environment, the pattern the deprecated ALM Accelerator used, because the environment then identifies the person ([ALM Accelerator (Deprecated)](https://learn.microsoft.com/en-us/power-platform/guidance/alm-accelerator/overview)). Test environments that are not production-type and not managed have the weakest attribution. There, the utility works mainly as a drift detector.

## Eight test-environment checks decide the final design

Each item below is undocumented or contradicted in Microsoft's documentation, and each one changes the architecture. The Purview check needs an environment of type **Production** that is set aside for testing, because sandboxes never send activity to Purview ([Power Platform activity logging overview](https://learn.microsoft.com/en-us/power-platform/admin/activity-logging-auditing/activity-logs-overview)).

| # | Verify | How | Design consequence |
|---|---|---|---|
| 1 | Whether component tables can be audited, and whether maker actions write audit rows | Query `EntityDefinitions` for `IsAuditEnabled` (Value, CanBeChanged) on systemform, savedquery, savedqueryvisualization, webresource, sitemap, appmodule, solution, entity ([Configure auditing](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/auditing/configure)). Enable the ones you can, edit and publish a form and a view in the maker portal, import a solution, then query `audits` by `objecttypecode` | If audit rows appear with `userid`, the Audit table becomes the primary "who" for forms and views in **every** environment. If not, forms stay dependent on Purview or stay unattributed |
| 2 | Whether customization messages accept plug-in steps | Run the documented `sdkmessage`/`sdkmessagefilter` query for PublishXml, PublishAllXml, ImportSolution(Async), ExportSolution, UninstallSolution. Confirm that systemform/savedquery Update are rejected in the Plug-in Registration tool ([Event Framework](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/event-framework)) | A registrable PublishXml gives "who published which components" in all environments through `ParameterXml`. PublishAllXml stays anonymous about which components were involved |
| 3 | What Purview actually records for metadata work | With auditing, Read logs and SAS logging on, run a scripted change set (add column, edit choice, edit form, edit view, publish, import/export/delete solution). ## Conclusion

The missing "who" is structural. Microsoft's current direction leans toward preventing untracked changes rather than logging them. Git integration is presented as the audit trail. Purview payloads are being stripped for privacy, and Microsoft may prune "unnecessary" operations. Block unmanaged customizations seals downstream environments. A utility that promises a perfect per-edit audit will overpromise. Three jobs are both achievable and valuable. The first is **continuous drift detection** in the environments ALM leaves uncovered: hotfixes in test and production, and non-managed environments. The second is **honest, confidence-graded attribution** that combines signals no single Microsoft surface brings together. The third is **outliving native retention windows** (90, 180 and possibly 30 days) by keeping every snapshot and signal in a store the team owns.

Two design implications follow. First, environment topology does more for attribution than code does. If each maker has a dev environment, deployments run only through service principals, and production is locked against unmanaged changes, "who" becomes bookkeeping rather than forensics, and the utility's job shrinks to reporting what falls outside that model. Second, much of the evidence base is undocumented behavior that Microsoft can change in any release wave. Package the eight checks above as an automated regression suite and re-run it after each wave, so that a silent change in what Purview or the Audit table records shows up as a failed test rather than as a gap in the audit trail.
